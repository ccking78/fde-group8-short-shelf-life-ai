# 短保供给 AI 原型：项目与前期资料采集复查

复查日期：2026-10-21。

用户已明确原型目标：基于前期收集的数据、资料，提出销售高峰前的补产/补货建议，并解释依据。本轮只核验开源项目、文档、源码与研究方法；未搜寻业务数据、未采集记录、未运行软件，也未搭建原型。

## 1. 修订结论

上一轮推荐适合学习库存业务与爬虫。面向已明确的原型目标，应补齐“原始证据—结构化事件与规则—决策时状态—计算建议—可追溯解释—验证”的完整路径。

建议优先顺序：

1. 先定义可重建的决策案例和字段规范，再组织前期资料搜集。
2. 公开文档用于形成有出处的流程、约束和规则；门店事件记录用于构造当时可见的状态与结果。
3. 用规则基线或显式约束模型计算补量、批次和可售时间；大模型负责抽取、交互和解释，并引用计算结果及资料。
4. 在没有齐全真实记录时，可用有出处规则、手动输入状态或明确标注的模拟状态，验证操作流程、约束与解释。真实业务收益需要后续真实记录或合适的试验支持。
5. 国际连锁真实四类记录继续作为优先证据；其缺失不必阻止原型交互与规则验证，但会限制效果结论。

以上为针对本题的工程建议，不是对任何开源项目开箱可用性的承诺。

## 3. 更贴近原型的开源组件

下表的项目能力来自官方资料；“本题职责”属于方案建议。无需一次引入所有组件。

| 环节 | 项目 | 本题职责与边界 |
| --- | --- | --- |
| 网页资料读取 | [Crawl4AI](https://github.com/unclecode/crawl4ai) | 小规模案例/说明页面的 Markdown 与结构化读取。其 [CSS/XPath/正则抽取](https://docs.crawl4ai.com/extraction/no-llm-strategies/) 可不调用 LLM。应同时保留原始页面、URL 和版本信息。若后续需要稳定批量调度，再选 Scrapy + Playwright 等主框架。 |
| 文档解析 | [Docling](https://github.com/docling-project/docling) | 解析文档、表格、OCR；保留页码/布局等可用的 provenance。官方 [DoclingDocument](https://docling-project.github.io/docling/concepts/docling_document/) 支持文本、表格、布局与来源信息。需要核查跨页表、单位和日期；其代码许可为 MIT，模型分别核对许可。 |
| 带原文位置的抽取 | [LangExtract](https://github.com/google/langextract) | 从长文提取规则、动作、原因、约束与适用范围，并保留原文位置及人工复核状态。Apache-2.0；项目 README 明确不是 Google 官方支持产品。 |
| 结构化事实查询 | [DuckDB](https://github.com/duckdb/duckdb) | 本地 SQL 查询与关联销售、批次、库存、报废和决策快照。官方支持 CSV/Parquet/JSON 等文件与 Python 接入，MIT。建议显式约定字段类型和单位。 |
| 补产/补货方案计算 | [OR-Tools](https://github.com/google/or-tools) | 将批量、开始/结束时间、资源冲突等显式建模；Apache-2.0。[排程示例](https://developers.google.com/optimization/scheduling/job_shop) 展示任务先后与资源互斥。批次寿命、需求区间、损耗与目标函数需要自行建立。 |
| 方案仿真，可选 | [SimPy](https://simpy.readthedocs.io/en/latest/) | 离散事件与有限容量资源，可模拟厨师/烤炉排队、批次完成和到期。其官方主仓在 [GitLab](https://gitlab.com/team-simpy/simpy)，MIT；GitHub 的 simpx/simpy 是 fork。短保库存状态和行为规则仍需自建。 |

### LangExtract 的来源定位需要验收

README 描述精确来源定位，但 [Extraction 数据结构](https://github.com/google/langextract/blob/main/langextract/core/data.py) 明确允许 char_interval 为 None；alignment_status 也区分精确、模糊和部分匹配。仅“能输出带来源的 JSON”不足以证明抽取正确。

本题建议：数值、时间和门店归属需人工核验或确定性校验；无法定位和只得到模糊匹配的项进入待复核区。原文位置属于抽取文本的定位，不自动证明属性、因果关系、跨文档门店归属或适用性正确。Docling 提取文本与原文页面之间也要保留映射。

### OR-Tools 的求解状态需要显示

[CP-SAT 官方文档](https://developers.google.com/optimization/cp/cp_solver) 要求整数约束，返回 OPTIMAL、FEASIBLE、INFEASIBLE、MODEL_INVALID 或 UNKNOWN 等状态。可按分钟、件或明确缩放后的单位建模，并记录缩放规则。

FEASIBLE 只能说明得到可行解；OPTIMAL 说明在所建模型内证明最优。UNKNOWN 不代表已证明无解。原型解释要同时展示求解状态、模型版本与关键假设。

## 4. 前期应收集的三组材料

以下是后续采集规范，本轮没有执行采集。三组材料可以先分别到位，再逐步关联，不要求每个来源同时包含所有字段。

### A. 原始证据与可引用规则

- 原始页面或附件，来源 URL、标题、发布者、发布日期、获取日期、文件版本/哈希。
- 品牌、国家、门店类型、业务类别、时间范围与使用权限说明。
- 规则原文、页码/段落/字符范围、适用商品、有效期和例外条件。
- 规则类别：可售寿命、生产耗时、最小批量、补货截止、折价/报废流程、店长调整触发条件等。
- 对供应商案例的改善声明保留基线、口径和观察期；缺失时记为未披露。

资料中的业务规则要由人确认适用性，再进入计算参数；不同国家、品牌和商品的规则不能默认通用。

### B. 结构化业务事件

| 记录 | 关键字段 | 额外要求 |
| --- | --- | --- |
| 销售 | store_id、sku_id、event_at、qty、unit、channel | 保留原始粒度与时区；区分销售金额、件数、退单。 |
| 库存/缺货 | observed_at、sellable_qty、stockout_start/end、观测来源 | 可售库存与系统账面库存分别记录；未知状态不填零。 |
| 生产/补货 | batch_id、计划/实际数量、started_at、ready_at/received_at、expiry_at | 在制和在途不能提前计入可售库存；同日多批次保持可区分。 |
| 临期/报废 | batch_id、expiry_at、discarded_at、qty、原因、其他去向 | 临期、过期、报废、折价、捐赠和调拨分开记录。 |
| 决策动作 | decision_at、原计划、调整动作、数量、理由、执行结果 | 当时原始计划可作比较基线；历史经理决策并不天然等于最佳答案。 |

每条事件均附 source_id、原始记录位置、观测/估计/人工输入/模拟标记及清洗版本。品牌与门店、商品映射要明确，不能仅凭相似名称自动合并。

### C. 可供原型调用的决策快照与验证案例

每个 case_id 对应“某门店、某商品或关联商品组、某个高峰前时刻”。至少保留：

- decision_at、时区、预测/计划区间、下一次复核时点。
- 当时已知的销售、库存，按批次分组的可售数量和到期时间。
- 在制/在途量、预计完成/到达时间，及这些预计当时的来源。
- 需求估计或低/中/高场景，生成时间与版本；无校准依据时不伪造概率。
- 批量倍数、最小/最大批量、制作/补货提前期、可用人手与设备、原料约束。
- 缺货与过量成本、残值等参数及其来源或“假设”标记。
- 原计划、调整动作、事后结果、缺失项和可验证的结论范围。

回放输入应满足当时已知的口径；event_at 与 available_at/known_at 分别记录。今天取得的历史文件，其抓取时间不能代替门店当时获得信息的时间。无法确认当时可知性的字段要标为不确定。

## 5. 原型建议的最小工作方式

这是后续搭建建议，本轮没有实现。

```mermaid
flowchart LR
    A[原始资料与事件] --> B[解析与人工确认]
    B --> C[结构化事件和规则]
    C --> D[冻结决策时状态]
    D --> E[需求场景与规则或约束计算]
    E --> F[补产补货方案及求解状态]
    C --> G[AI解释与来源引用]
    F --> G
    G --> H[店长接受或修改]
```

### 建议的计算与解释职责

- 首版以规则基线、需求区间和显式约束为核心。原计划、简单规则与约束优化三种方案使用一致的状态和假设进行比较。
- 大模型从已确认的规则和计算输出组织解释。解释同时给出库存和需求依据、时间与产能约束、规则出处、假设与缺失字段。
- 补产与外部补货使用不同的可行性参数，分别计算制作完成或交付可售时间。
- 遇到库存、到期时间或关键提前期缺失时，输出需要补充的信息；缺失不能被处理为零，也不能用语言模型猜补。
- 首版范围建议限制为一个门店类型、一个商品类别和一个明确高峰，验证完成后再扩到关联商品与门店。这里没有预设用户的实际门店或商品。

建议页面至少显示：决策时状态；建议补多少、何时开批/下单、何时可售；与原计划的差异；缺货/剩余风险在不同需求场景中的变化；依据链接；假设、缺失项与求解状态；接受/修改入口。

## 6. 数据到位程度决定能验证什么

| 到位程度 | 可以先验证 | 结论边界 |
| --- | --- | --- |
| 业务资料 + 人工或模拟输入状态 | 输入流程、规则适用性、数值可行性、解释与引用 | 演示数据必须明确标记；不能声称真实降低缺货或报损。 |
| 可关联的真实事件 + 当时状态/动作 | 历史时点的信息可知性、硬约束、解释，以及实际动作下的事实结果 | 改变动作后的结果不在原始历史中直接可见。 |
| 经校准的仿真或其他合适评估设计 | 在明确需求/库存假设下比较替代方案，做敏感性分析 | 仿真中的改善属于模型估计。真实业务效果还需相应验证。 |

缺货时，销售没有包含全部未满足需求。把销售直接当完整需求会影响补量与方案评价；相关原始研究明确讨论这一观测限制：[Chen、Chao、Shi，2021](https://pubsonline.informs.org/doi/pdf/10.1287/moor.2020.1084)。本题应保留缺货时段，并区分真实观测的缺货和估计的损失销量。

历史回放可检验是否泄漏未来信息、是否违反约束和解释是否忠于证据。若更改了生产动作，货架数量、后续缺货和销量都可能变化；替代方案结果需要额外模型或试验，不能套用原动作下的历史结果。

## 7. 原型验收建议

不设置未经依据支持的统一最低天数或样本数；先检查字段关联、可知时间、重要状态覆盖与留出的验证区间。

- 抽取层：数字、单位、时间和归属能回查；重复、矛盾、缺失有明确状态。
- 决策层：批量、资源、原料、寿命和可售时间约束满足；展示求解状态；无解或信息不足有相应输出。
- 解释层：事实、假设与估计可区分；每项理由对应资料或计算结果；数字与计算输出一致。
- 回放层：按时间冻结输入，验证区间单独留出；同一来源的重复材料不能同时用来调提示词并声称是独立验证。
- 结果层：在实际观测允许的范围内报告缺货时长与报废数量；估计损失销量、预计成本等保留假设及敏感性，不将模拟改善写成真实节省。

首批案例应覆盖：库存已足够；库存不足且来得及补；补产完成晚于高峰；旧批次高峰前到期；多商品争用同一资源；需求不确定；关键输入缺失；资料规则冲突。可先用明确标注的模拟状态检验这些分支，再用真实案例验证适用性。

## 8. 最终选型建议

面向这个原型，优先准备原始证据、结构化事件/规则、决策快照和验证案例四类交付物。

- 资料读取与解析：Crawl4AI 或按来源选用的爬虫 + Docling。
- 长文抽取与原文复核：可选 LangExtract；规则进入计算前人工确认。
- 事件查询与计算：DuckDB + 自建规则基线，约束复杂时接 OR-Tools。
- 方案比较：需要排队与资源交互时接 SimPy，保留所有模拟假设。
- 业务学习：ERPNext 看字段与事件，Stockpyl 看成本基准，frePPLe 看排程表达。

模型供应商、界面框架、运行方式与具体目标函数待真正搭建时依已有环境和数据确定。本轮没有因此扩大到模型训练、实际爬取或部署。
